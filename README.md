# Blueprint — SMB Commerce Operations Agent

> **Work in progress.** This blueprint is under active construction and hands-on testing. Its README will grow as rounds land.

An operations agent for a small online retailer, built on **Meta Muse Spark**. It watches the store's own numbers — orders, refunds, inventory, ad spend, email flows, expenses — computes the operating picture in code, flags what needs attention, drafts the growth plan and the copy, and then stops: a separate guardian screen checks every draft, and a named human approves before anything sends, publishes or spends.

Money is computed in code, never by the model. Every figure in a plan traces to a stored fact with provenance. Every draft is an artefact; every approval is a named act bound to the draft's content.

The demonstration business is a fictional home-goods retailer; its data is generated in-repo so every planted pattern — a stockout brewing, an ad set decaying, a duplicate charge — can be checked by hand.

This is Trida's open, production-grade take on the pattern Meta launched as **Muse for Small Business** (2026-09-29): a Muse agent over a small business's connected stack — store, payments, books, email, ad accounts — doing the growth plan, the financial review and the email-automation audit, with the audit trail a services firm needs before it deploys anything similar for a client.

## Quickstart

```bash
make install     # uv sync --extra dev   (no uv? make install-pip)
make demo        # generate the dataset, print the operating picture
make test        # pytest
make evals       # the eval gate
make serve       # FastAPI on http://localhost:8000 — /health, /readiness, reads
make cli         # the CLI surface (the ledger)
```

Or with Docker: `docker compose up` brings up the agent, Postgres 16 and a SeaweedFS S3-compatible object store (service name `minio`).

No key is needed for any of the above. The default model profile is a deterministic offline composer; the hosted Muse Spark profile is wired through the Meta Model API and fails closed until `META_MODEL_API_KEY` is set (see `.env.example`).

## What Round 1 builds

- **Fact store with provenance (Law 3).** Orders, refunds, inventory positions, daily ad spend, email-flow definitions and expense lines enter only through an ingest port that refuses any fact without a source system and an as-of date. SQLite by default; `DATABASE_URL` switches to PostgreSQL 16. Numbered SQL migrations run at startup in both dialects.
- **A gold-by-construction dataset.** The generator writes one year of Hartwell Home Goods through that same port, from stated constants: a hero SKU, a fast mover whose restocks stop after week 39 so its cover drains to exactly 21.0 days, an ad set whose attributed revenue decays by a factor of 0.94 a week, a duplicated vendor charge on adjacent days, and an email platform where the winback flow was never defined.
- **The commerce ledger (Laws 1 and 4).** Revenue, refunds, gross margin, refund rate, inventory cover days per SKU and ad return per set — Decimal arithmetic over the stored facts, stored as an insert-only, content-addressed artefact. A verifier re-performs every figure by a second route; tamper with a stored fact and verification names it.
- **The model port (Law 6).** One governed port for all model calls. Profiles: `meta-muse` (Muse Spark via the Meta Model API, OpenAI-compatible shape) and `offline`. Every call is written to a per-run cost ledger with tokens, profile, tier and a cost computed from the published price table — Standard $1.25 / $4.25 per 1M input/output tokens, Contributor $0.10 / $0.20 — and totals reconcile exactly. Standard is the default tier because Meta does not train on its data; Contributor must be chosen explicitly and is stamped on every record.
- **Surfaces.** A LangGraph loop (ingest → compute → verify), FastAPI reads (`/facts`, `/ledger`, `/ledger/verify`, `/model-calls`), a CLI, and a demo that prints the operating picture with the planted patterns visible in the computed figures.

## What Round 2 builds

- **Diagnosis pack I (Law 5).** The rules are data in a versioned pack (`2026.10.1`): a stockout horizon of 24.00 cover days against a trailing 28-day velocity, and ad-decay bars — a set is judged only above $2,600.00 total spend and 8 weeks of history, and is decaying when its latest-week return on spend falls to at most half its first-week return (a set retaining 90% or more is steady by construction). The pack's thresholds are stated in the module, so the same inputs always re-perform to the same findings.
- **Findings as artefacts (Law 4).** The stockout diagnosis names the Washed Linen Throw: 210 on hand, 21.00 cover days at 10.00 units a day, out on 2026-01-25. SKUs with adequate cover are named nowhere; a SKU with no stock or no sales reads as no-data, never as zero risk or zero cover. The ad-decay diagnosis names Social — Seasonal Decor: return on spend 4.0000 in its first week, 0.1704 in its last, a decay factor of 0.0426. The steady sets (3.5000 and 2.0000 all year) are named nowhere; a set below the spend bar is named as unjudged, with the reason.
- **Re-performance before existence.** Each diagnosis is computed from the head ledger artefact's figures and re-performed from the stored facts by a second route before the finding set is stored. One wrong figure — or a ledger that no longer matches the fact set, down to a fact edited behind the store's back — refuses the whole set: a refusal artefact is recorded and no finding is stored. A stored finding set can be re-verified at any time through the same second route.
- **Surfaces.** The LangGraph loop gains a diagnose node between compute and verify. FastAPI reads (`/diagnosis/stockout`, `/diagnosis/ad-decay`, their `/verify` companions, `/diagnosis/refusals`), CLI commands (`diagnose`, `diagnose-verify`, `refusals`), and the demo walks both diagnoses right after the ledger.

## What Round 3 builds

- **Diagnosis pack II (Law 5).** The pack moves to `2026.10.2`, adding expense and refund rules; the pack I sections carry over unchanged and the `2026.10.1` pack is kept verbatim, so a finding set stamped with the earlier version still re-performs under its own version. Expense bars: an exact duplicate is the same vendor charging the same amount again within 7 days; an amount outlier is a charge above 3.00x that vendor's own median charge (a vendor with fewer than 3 charges is unjudged for outliers, with the reason named); a vendor's first charge above $1,000.00 is named as informational, in its own class. Refund bar: a SKU's refund rate — refund amounts over gross revenue, from the ledger's per-SKU figures — above 0.040000, judged only over at least 1,000 units sold; below that a SKU reads as unjudged, never as clean.
- **Findings as artefacts (Law 4).** The expense diagnosis names the planted duplicate: PackShip Co, $349.00 on 2025-11-14 and again on 2025-11-15, both fact ids on the finding's face. No charge clears 3x its vendor's median (every vendor bills a constant amount), so there are no outliers; the Studio Lease ($2,400.00) and Northgate Logistics ($1,250.00) first charges are named as informational only. The refund diagnosis names the Ceramic Vase: $9,568.00 refunded against $191,360.00 gross — a rate of exactly 0.050000. Every other SKU sits under the bar and is named nowhere.
- **Re-performance before existence, again.** Both new diagnoses run under the same discipline as pack I: computed one way, re-performed from the stored facts by a second route before the finding set may exist; a mismatch — or a ledger gone stale against the fact set — records a refusal artefact and stores no finding. The CLI diagnose commands and the demo now walk all four packs.

## What Round 4 builds

- **Diagnosis pack III — the email-flow audit (Law 5).** The pack moves to `2026.10.3`, adding an audit section; every earlier section carries over unchanged and the `2026.10.1` and `2026.10.2` packs are kept verbatim, so a finding set stamped with an earlier version still re-performs under its own version. The pack states the catalogue of flows a store of this kind is expected to run — the five flows the email platform defines (welcome, abandoned cart, post-purchase, browse abandonment, replenishment) plus the winback flow it never defined — each with a trigger and an expected step shape.
- **Findings as artefacts (Law 4).** A catalogue flow with no definition is a missing finding; a defined flow that is not active is a dormant finding, in its own class; an active flow with fewer steps than the catalogue's shape is a step-shortfall finding; and where a flow definition carries per-step send delays, any delay beyond the pack's 720-hour sanity bar is a delay-breach finding (the Hartwell export carries no delays, so that rule grades nothing there). On the Hartwell facts the audit names exactly one finding: winback is missing. Every defined flow grades healthy and is named nowhere, and the audit writes artefacts only — the defined flows are byte-identical before and after it runs.
- **Fixes are drafts, never edits.** For each missing or dormant flow the audit emits a draft flow proposal artefact — the catalogue's trigger, step count and step delays for that flow, structure only, no copy — stamped as a proposal that changes nothing until a later approval round acts on it. The winback proposal proposes a `customer_lapsed` trigger, 2 steps, delays of 0 and 336 hours.
- **Re-performance before existence, again.** The audit runs under the same discipline as the other packs: computed one way, re-performed from the stored facts by a second route before the finding set may exist, proposals included; a mismatch records a refusal artefact and stores no finding. The LangGraph loop's diagnose node now runs all five diagnoses; the API, CLI and demo walk the audit and its proposals alongside the other packs.

## What Round 5 builds

- **The growth plan artefact (Laws 1, 4 and 5).** One plan, assembled from the current computed record: an operating summary that copies its figures from the head ledger artefact — each figure citing the ledger artefact id and the field it came from — a priorities section ranking the five diagnosis families' findings, and an actions section that references the finding artefacts and the audit's draft flow proposal by id. The plan proposes actions; it performs none, and says so on its face. No prose is drafted in this round — narration is Round 6's job, over this verified plan.
- **The ranking rule is pack data.** The plan pack (`2026.10.1`, its own versioned pack, kept verbatim alongside any future version) states the family order — stockout risk before ad decay before expense anomalies before refund anomalies before email-flow audit gaps — and the tie-breaks inside a family: exposure descending (the headline magnitude the finding itself carries, named per family in the pack: trailing units, total spend, charge amount, refunded amount; audit findings are structural and carry no exposure), then the finding's identity key ascending. On the Hartwell record the order is: the Washed Linen Throw (280 trailing units), Social — Seasonal Decor ($26,000.00 of spend), the PackShip duplicate ($349.00), the Ceramic Vase ($9,568.00 refunded), and the missing winback flow.
- **Empty-state honesty.** A diagnosis family with no findings contributes an explicit no-findings entry to the plan, naming the diagnosis pack version that judged it — never a silently absent section. A family whose diagnosis is refused blocks the plan whole: a plan refusal artefact records the refusal it names, and no plan is stored.
- **Figure verification before existence.** Before a plan may exist, every figure in it is re-resolved against the artefact it cites and the priorities and actions are re-derived from the cited finding sets by a second route. A figure that does not match its source, or a citation to a superseded or refused artefact, records a plan refusal and stores no plan. Any stored plan can be re-verified at any time through the same route; re-running the assembler over a moved record supersedes the old plan by link, never by edit.
- **Surfaces.** The LangGraph loop gains a plan node between diagnose and verify. FastAPI reads (`/plan`, `/plan/verify`, `/plan/refusals`), CLI commands (`plan`, `plan-verify`, `plan-refusals`), and the demo assembles and verifies the plan right after the audit, printing its priority order.

## What Round 6 builds

- **The model enters the loop — through the port, and only the port (Laws 1 and 6).** A drafting service produces three drafts over the verified record, every one a governed model call recorded in the cost ledger: the **plan narrative**, prose that walks the head growth plan's priorities in the plan's own order; the **winback email copy** for the audit's draft flow proposal — a subject and a body per proposed step; and a **draft budget-action note** for the decaying ad set. Each draft is an insert-only artefact bound to the exact artefacts it drafts from and stamped with the model profile, the tier, and the cost-ledger record id of the call that produced it.
- **The drafting contract.** The service hands the model a *figure sheet* — the only figures the draft may state, each entry carrying the artefact id and the field it resolves to — and the model replies with the prose plus a structured claims list citing artefact and field for every figure. The offline profile composes its reply from the sheet alone, deterministically; a hosted profile answers the same contract.
- **Figure discipline, enforced in code (Law 1).** Before a draft may exist, a verifier resolves every claim against the artefact it cites, and scans the prose for figure tokens: any number the prose states that no claim carries is itself a failure. A draft with an invented or mismatched figure is refused whole — a draft refusal artefact records the offending claim and no draft is stored as usable. `verify` re-performs any stored draft at any time, and re-checks the stamped call against the cost ledger.
- **Honest states.** A draft is a draft: its status says so on every surface, and nothing in this round calls a draft approved, sent or published. The guardian screen is Round 7 and approval is Round 8.
- **Surfaces.** The LangGraph loop gains a draft node between plan and verify, and the verify node re-performs the drafts alongside everything else. FastAPI reads (`/drafts`, `/drafts/plan-narrative`, `/drafts/winback-copy`, `/drafts/ad-budget-note`, their `/verify` companions, `/drafts/refusals`), CLI commands (`draft`, `drafts`, `drafts-verify`, `draft-refusals`), and the demo drafts the narrative and the winback copy from the verified plan, printing each with its verification status, tier and cost.

## What Round 7 builds

- **The guardian screen — Law 2's second gate (the Sentinel pattern).** Every draft must pass a separate screening before it may be listed as awaiting approval. The verdict is an insert-only artefact bound to the draft's artefact id *and* its content hash, stamped with the version of the policy pack that judged it: a draft edited in any way is a new artefact with no verdict, and verdicts never transfer across hashes.
- **Hard lines judged in code, from a versioned pack.** A discount promise beyond the cap the business never authorised — in digits or in words ("forty percent off", "half off"); a claim that does not resolve against the artefact it cites; a figure stated in the prose that no claim carries, scanned in digit form and in *word* form ("nine hundred shoppers"), which the drafting gate's digit scan cannot see — the guardian is a second net, not a rerun of Round 6; the pack's prohibited content classes (guaranteed-results language, competitor disparagement against pack-named competitors, regulated advice claims); and a source artefact superseded or refused since the draft was made.
- **Judgement calls screened by the model, as their own governed call.** Tone and pressure tactics, and perk claims that mislead by omission, are decided by a separate screening call through the model port under a screen-sheet contract — one structured verdict naming an outcome per rule id, recorded in the cost ledger like every other call. The offline profile answers deterministically from the pack's stated phrase lists, so screening runs without a key; a reply that cannot name the pack's rules blocks the draft rather than passing it.
- **The gate is enforced in the service.** A draft appears as awaiting approval only when its latest verdict passes *and* re-verifies clean — the verifier re-performs the content hash, every code-judged rule outcome under the verdict's own pack, and the stamped screening call's cost. Blocked drafts carry their named blocking rules on every read surface. Re-screening is a new verdict under the pack that judges it; the old verdict stays. Approval itself — the named human act — is Round 8; this round builds no approval surface, only the gate that feeds it.
- **Surfaces.** The LangGraph loop gains a screen node between draft and verify, and the verify node re-performs the verdicts too. FastAPI reads (`/guardian/verdicts`, `/guardian/verdicts/{id}/verify`, `/guardian/awaiting-approval`, `/guardian/blocked`), CLI commands (`screen`, `verdicts`, `verdicts-verify`, `awaiting-approval`), and the demo screens the three drafts clean, then shows a planted bad draft — written straight into the store, past the drafting gate — blocked with its rules named and kept out of the queue.

## What Round 8 builds

- **The approval queue — Law 2's named human act.** Approval and rejection are insert-only act artefacts, never an editable status on the draft. An approval act names the approver, the draft artefact id *and* its content hash, and the passing guardian verdict it relies on; a rejection act names the rejecter and a reason from a stated vocabulary (`not_ready`, `wrong_tone`, `figures_unclear`, `timing`, `other`) plus free text. The queue — awaiting, approved, rejected — is a view derived by folding the acts over the guardian's gate, so no surface can edit a draft into the approved column, and an approval act that does not re-verify is excluded from the approved list.
- **Refused attempts are recorded.** Approval is refused — with an approval-refusal artefact recording the attempt and the reason — when the draft has no passing verdict, when the verdict's hash differs from the draft's current hash, when the draft's source has been superseded or refused since the verdict, or when the draft already carries an approval (no double-approval). A rejected draft leaves the queue and cannot then be approved; its rejection stays in its history.
- **Approved is not executed.** Every approval act and every approved queue entry reads `approved — not sent`: the blueprint executes nothing against real systems, and execution against Shopify, Klaviyo or any other vendor system is out of scope by design.
- **Stale approvals are marked, never silently clean.** An approval snapshots the inputs it binds — the verdict, the draft's sources and their heads, the head ledger. When any of them moves afterwards (a new ledger, a superseded plan, a new verdict under a changed pack), the act stays as history and still verifies as a true record, but the approved surface derives staleness at read time and marks the approval STALE with each moved input named.
- **Surfaces.** FastAPI reads and acts (`/approvals/queue`, `/approvals/awaiting`, `/approvals/approved`, `/approvals/rejected`, `/approvals/refusals`, `/approvals/history/{draft}`, `/approvals/acts/{id}`, `/approvals/acts/{id}/verify`, `POST /approvals/approve`, `POST /approvals/reject`), CLI commands (`queue`, `approve`, `reject`, `approvals-verify`, `approval-history`, `approval-refusals`), and the demo approves the three clean drafts by a named approver, rejects a fourth screened draft with a stated reason, and shows the planted bad draft's approval attempt refused and recorded.

## What Round 9 builds

- **The morning board — the operator's opening view, re-derived from artefacts.** One fold of the current record: a headline copying the operating figures from the head ledger artefact (each figure citing the ledger field it came from), the current findings across the diagnosis and audit packs in the growth plan's ranked order — every finding's figures copied from the finding artefact it cites, no-findings families kept as explicit coverage — the stock risks called out on their own (the Washed Linen Throw: 210 on hand, 21.00 cover days, out 2026-01-25 at 10.00 units a day), and the approval picture exactly as Round 8's queue folds it.
- **The board invents nothing (Laws 1 and 5).** Drafts awaiting approval are the guardian-passed, not-yet-acted-on drafts; blocked drafts carry their named blocking rules; approved drafts read `approved — not sent`, with stale approvals marked STALE and their moved inputs named, the way the approval queue marks them; rejected drafts carry their stated reasons. A draft that was never screened appears in no section — it is counted as unscreened, never quietly listed as awaiting.
- **Re-derived at read time, never stored as truth.** The board is composed fresh on every read and returned as an in-memory, content-addressed artefact; it is never inserted into the store, so no surface can edit anything onto it. It pins the inputs it folded — the ledger head, the plan head, each diagnosis head, the latest guardian verdict per draft, the latest approval and rejection acts — so later movement is detectable rather than silent.
- **A verifier re-performs the board end to end.** The sections are recomposed by a second route — from the derived queue folds and the finding sets directly — every headline and finding figure is re-resolved against the artefact it was copied from, and the pins are compared against the current heads. A board whose contents do not re-derive from the record — a figure changed, an entry dropped, a stale approval shown clean, a pin moved — fails verification with the problem named; a board folded before the record moved fails the same way. The LangGraph loop gains no node: the board produces nothing, it composes at read time from what the pipeline steps left behind, like the queue's fold.
- **Surfaces.** FastAPI reads (`/board`, `/board/verify`), CLI commands (`board`, `board-verify`), and the demo prints the board after the approval queue walk — headline, findings, the stock risk, and the approval picture with its counts.

## What Round 10 builds

- **The production Postgres profile, proven rather than asserted.** `DATABASE_URL` has selected PostgreSQL 16 since Round 1; this round stands the whole system up on it and grades the claim that the dialect is invisible: the full core walk — ingest, ledger, all five diagnoses, plan, drafting, guardian screen, approvals, morning board — produces **byte-identical artefacts on Postgres and on SQLite over the same record (parity gap 0)**, the walk and the canonical snapshot it is graded by defined once in `smb_commerce/parity.py` so the test leg and the smoke can never grade different things.
- **Two real dialect bugs the first live run found, fixed at the owning layer.** (1) psycopg returns text columns as `bytes` when the database encoding is SQL_ASCII, and b'0001' never equals the migration filename's '0001' — so **a second boot against an already-migrated SQL_ASCII database re-ran its migrations and crashed on the existing tables**. The store now decodes bytes to text at its one row-materialisation point, and the migration runner normalises the applied versions the same way; text reads back as text on either dialect and repeat boots apply nothing. (2) A Postgres connection that has read sits idle-in-transaction holding locks that blocked a `DROP SCHEMA` indefinitely — the store gained `close()`, and the leg and the smoke close their stores before dropping their throwaway schemas.
- **The in-suite parity leg.** `tests/test_postgres_parity.py` runs the walk on both dialects and diffs the snapshots, checks the migrations apply cleanly and re-run idempotently, and checks text reads back as text. It runs only when `SMB_TEST_DATABASE_URL` names a database — without it, the leg skips cleanly and the default suite is unchanged. The leg refuses a database whose name does not look like a test database, and works inside its own throwaway schema, dropped when it finishes. Run it with: `SMB_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:5432/smb_test uv run --extra dev pytest tests/test_postgres_parity.py`.
- **The production smoke.** `scripts/prod_smoke.py` (`make smoke`) builds the app from `DATABASE_URL` in a throwaway schema — `SMB_POSTGRES_SCHEMA` names a schema the same way for any run — applies the migrations, checks a second boot is idempotent, answers `/health` and `/readiness` on the real app, runs the core walk on Postgres, and diffs the artefacts against a full SQLite walk, printing `SMOKE PASS` and exiting non-zero on any failure. Without `DATABASE_URL` it fails cleanly rather than pretending to have smoked anything.

## What Round 11 builds

- **Connector ports v2 — versioned exchange contracts.** Facts now arrive the way real feeds deliver them: as batches under an exchange contract (version `2026.11.1`). Each contract states its batch envelope (contract name, contract version, source system, as-of), the record kinds it carries and the exact (kind, source) pairs it accepts, and its provenance requirements. The registry covers the Shopify-shaped storefront orders and warehouse inventory exchanges, the Stripe-shaped payments export that carries refunds, the QuickBooks-shaped books feed (its stated as-of lag bound is the monthly close's 45 days, not the daily feeds' week), the Klaviyo-shaped email-platform definitions, and the ads manager's exchange in the same pattern. Contracts are stated data and local doubles implement them; no real vendor is contacted.
- **Whole-batch quarantine.** A batch that violates its contract — an unknown contract or contract version, a source the contract does not govern, a record missing provenance, sources mixed inside one batch, a kind the contract does not carry, a payload that fails its model, an envelope whose as-of precedes or trails its records past the stated bound — is quarantined **whole**: no partial ingestion, nothing from the batch reaches the fact store, however many of its records were conforming. Every violation found is named, from a closed vocabulary; the judgement never stops at the first problem.
- **The quarantine is on the record.** Each quarantined batch is recorded as an insert-only artefact naming the contract, every violation, the record count and digests, and the batch's content hash — the artefact's id is the hash's address, and a verifier re-derives the hash chain from the named material, so a forged or edited quarantine fails verification. Re-presenting the same bad batch returns the same artefact; it is recorded once.
- **Conforming batches keep v1 semantics.** A batch that passes its contract goes through the Round 1 ingest port exactly as before: store-level duplicates and conflicts keep their meaning, and replaying a batch lands nothing twice. The Hartwell dataset now loads as six contract batches, and everything downstream — ledger, findings, plan, drafts, guardian, approvals, board — is byte-identical to the v1 record; the only difference is the facts' insertion order, which follows the batches. No migration was needed: quarantines live in the existing artefact store.
- **Surfaces.** The service exchanges batches and reads quarantines; FastAPI adds the registry read (`/connectors`), the exchange (`POST /connectors/exchange`, 422 with the quarantine's id and violations when a batch is refused), and the quarantine reads (`/connectors/quarantines`, `/connectors/quarantines/{id}`, `/connectors/quarantines/{id}/verify`); CLI adds `connectors`, `quarantines` and `quarantine-verify`; and the demo replays a batch (all duplicates), then shows a planted broken books batch — wrong contract version, one record stripped of provenance — quarantined whole with its violations named and the fact count unmoved.

## What Round 12 builds

- **The Muse profile, verified as far as a stub can verify it.** The hosted `meta-muse` profile already existed and failed closed without `META_MODEL_API_KEY`; this round adds the verification path around it. `model-profile` (CLI and `GET /model-profile`) resolves the configured profile and reports its state without calling anything: for `meta-muse`, the model id and where it came from (the environment, or the built-in default `muse-spark` — configurable, and labelled unverified until a live account confirms it), the base URL, the tier, whether a key is present, and fail-closed proved by attempting the construction. A probe (`probe_meta_muse`) runs one governed call end to end against a caller-supplied transport — in the test suite and the eval gate, a local double of the Meta Model API — grading the request shape, the auth header, the tier stamp on the ledger record and the exact Standard cost identity. **No live call is made anywhere in this round: there is no Meta Model API key in hand, and every report carries `live_call_made: False`. The live leg stays pending a key, stated plainly.**
- **Context management for the 1M-token window.** Prompts were assembled ad hoc at the call sites with no budget and no record. Now a versioned context policy (window 1,000,000 tokens as published for Muse Spark, minus a stated output reserve; a whitespace-word token estimator — the same one the offline profile prices by, deterministic and stated as an estimate) governs assembly at the one choke point every call passes through, the governed model port. The system prompt and a request's sheet lines are pinned — they carry the figures and the contract — and the rest is narrative: over budget, narrative lines drop **oldest first** behind one marker line naming the policy, the rule and the count dropped, the minimum the budget forces; pinned material alone over budget **fails closed** and the call never happens. Every governed call records its assembly as an insert-only `context_assembly` artefact (policy version, budget, token counts before/after, what was dropped) whose arithmetic a verifier re-performs. Uncompacted calls keep their exact pre-Round-12 call ids, so nothing downstream moved; today's real contexts run to a few hundred words, so compaction is graded with oversized fixtures.
- **Cost analytics over the ledger.** The rate card is now versioned data (`2026.11.1`) carrying the published Muse Spark rates — input, cached input and output for both tiers (Standard 1.25 / 0.15 / 4.25, Contributor 0.10 / 0.002 / 0.20 per 1M tokens) — and the pricing function already applies the cached rate to any cached portion a caller hands it; recorded calls price input and output, because no usage source in this codebase reports a cached split yet. The graded identities stand exactly: Standard 1M-in/1M-out is $5.500000, Contributor $0.300000. `CostAnalytics` aggregates the recorded ledger in code — totals plus breakdowns by profile, tier, model and run, each summing exactly to the total — and reconciles every recorded cost against the card across all runs, naming any mismatch. One grain is honestly absent: call records carry no timestamp, so there is no by-day breakdown; runs are the finest grain on the record and the summary says so. Surfaces: `GET /costs`, `GET /model-profile`, `GET /contexts`; CLI `costs`, `model-profile`, `contexts`; and a closing demo beat over the walk's own record. The eval gate gains four zero-tolerance counters (57 in all) for the profile, context and cost invariants. No migration was needed: context records live in the existing artefact store.

## What Round 13 builds

- **Access control: a versioned role pack.** The record now answers to the shop's staff structure. Four roles — **owner**, **operator**, **bookkeeper**, **viewer** — and a permission matrix held as data in a versioned pack (`2026.11.1`), enforced by lookup, never by conditionals scattered through the surfaces. The matrix:

  | Surface | Owner | Operator | Bookkeeper | Viewer |
  |---|---|---|---|---|
  | Facts, ledger, diagnoses | read | read | read | — |
  | Plan, drafts, guardian, approvals, board | read | read | — | — |
  | Connector registry, quarantines | read | read | read | — |
  | Costs, model calls, context records | read | read | read | — |
  | Configuration (model profile) | read | read | read | read |
  | Ingest, connector exchange | run | run | — | — |
  | Diagnose, plan, draft, screen runs | run | run | — | — |
  | Approval acts (approve / reject) | **act** | — | — | — |
  | Digests (read — content-gated per digest) | read | read | read | read |
  | Digest generation, subscription record | run/read | run/read | — | — |

- **Enforcement at the service boundary, so the surfaces cannot diverge.** Both surfaces resolve a caller identity the same way — a named actor plus a role, from the `X-SMB-Actor` / `X-SMB-Role` headers on the API or the `--actor` / `--role` flags on the CLI, through one resolution function — and pass it to the service, which refuses what the pack refuses. Only the owner may record an approval act: the operator runs the pipeline but cannot approve what their own pipeline produced, which keeps Law 2's named human independent of the drafting machinery. A role-gated approval attempt is refused **before any lookup of the draft** and recorded like every refused approval — an approval-refusal artefact naming the actor and the role problem — so the refusal is identical for a real draft and an absent one. The bookkeeper reads the money record and nothing of drafts, approvals, the plan or the board; the viewer is the named least role, holding no record permission at all. In-process flows (the demo, the eval gate, the graph, the parity walk) act as a stated internal identity — the owner-operator running their own deployment — never as a surface default.
- **Existence hiding.** A caller whose role may not see a resource gets the response an absent resource gets: the same 404 and detail text for a single read, the empty list and a zero count for a list, the empty queue fold, the zero cost summary, "no board yet" for the board. Nothing leaks through counts, summaries or error detail, and the grading is byte-level: on the API, probing a real artefact, quarantine, verdict or fact id as a forbidden role returns a response identical in status and body to probing an absent id; at the service layer the forbidden read returns the absent form itself. Unauthenticated calls — no actor, no role, an unstated role — resolve to an anonymous caller that holds nothing and fails closed everywhere on the record. `/health` and `/readiness` stay open: they are infrastructure probes and carry no record data.
- **Honest limits, stated.** Identity here is **presented, not authenticated**: this round binds roles to callers who present them, inside a deployment that trusts its callers to do so — it is an access-control layer, not an identity provider. Scoped tokens (Round 18) are the round that authenticates a presented identity; they will resolve to the same caller shape this round defines. Surfaces: every API record endpoint and every CLI command takes the caller; the demo gains an access beat (a viewer probing a draft and getting "not found", the bookkeeper reading the ledger but not a draft, an operator's approval refused and recorded). The eval gate gains three zero-tolerance counters — existence leaks, role escalations, unroled actions accepted — 60 in all. No migration was needed: the pack is code, and refusals live in the existing artefact store.

## What Round 14 builds

- **Subscriptions: who receives what, on the record.** A subscription is an insert-only artefact naming a staff member (actor + role) and a cadence — `daily`, or `weekly` (the seven-day week ending on a stated date). Unsubscribing inserts a successor state that supersedes the active one, and the current state is the fold of the chain, the way the approval queue folds acts. Re-subscribing an active subscription is a no-op. Writing subscriptions is an owner/operator action under the access pack, and the record itself reads owner/operator only — it names the staff.
- **Digests: the morning board's stored, per-role counterpart.** Where the board is re-derived on every read and never stored, a digest is folded once for a stated period and a stated role, pinned to the heads it folded, and kept as a content-addressed artefact. Its sections are decided by the Round 13 pack, section by section — headline under `ledger:read`, findings and stock risks under `plan:read`, the approval picture under `approvals:read`, the cost summary under `costs:read` — so the owner's and operator's digests carry all five sections, the bookkeeper's carries headline + costs, and the viewer's carries **no section at all**: a digest cannot contain what its role may not read, and a section the role may not read is absent, never redacted in place. Every figure is copied from a computed artefact and cites it, and the verifier re-performs a digest by a second route — fresh fold, figure re-resolution, pin and section comparison — exactly as the board's verifier does; a digest folded before the record moved fails verification, like a stale board.
- **Generation is subscription-driven and idempotent.** Generating a cadence produces exactly one digest per active subscription of that cadence. A digest's identity is its content (role, cadence, period, pins, sections), so two subscriptions for the same role and cadence are served by the one artefact, and re-running the same period over an unmoved record inserts nothing — every digest reports back `existing`.
- **Reads are gated by content, not address.** A caller may read a digest when they hold every permission the digest's included sections required: the bookkeeper probing the owner's digest gets the same 404 as probing an absent id — byte-identical on the API, the absent form at the service layer, on the dedicated reads and on the generic artefact reads alike — while the viewer's empty digest is readable by any identified staff caller, because there is nothing in it anyone may not see.
- **Stated limits.** A digest is purely code-assembled — **no model call is made and there is no narrative prose in it**; prose stays Round 6's governed drafting path. **Nothing is sent anywhere**: a digest is generated into the record and read back through the surfaces by a caller whose role may read it. Delivery to a mailbox or a phone would be something leaving the building, which Law 2 reserves to the guardian + named-approval path — not built here, and not pretended. Figures are the record's computed figures as of the head ledger's as-of; the period is the reporting label the snapshot is pinned under, not a per-period re-computation (the record carries no per-period ledger — the same grain limit Round 12 states for costs). Surfaces: `GET/POST /subscriptions`, `POST /subscriptions/unsubscribe`, `POST /digests/generate`, `GET /digests`, `GET /digests/{id}`, `GET /digests/{id}/verify`; CLI `subscriptions`, `subscribe`, `unsubscribe`, `digest-generate`, `digests`, `digest-verify`; the parity walk now generates both cadences, so subscriptions and digests are inside the byte-identical Postgres/SQLite snapshot; the demo gains a digest beat. The eval gate gains three zero-tolerance counters — digest figure mismatches, digest role leaks, duplicate digests — 63 in all. No migration was needed: subscriptions and digests live in the existing artefact store.

## What Round 15 builds

- **A red team, graded on invariants.** A versioned adversarial corpus (`tests/test_redteam.py`, 25 test functions, 31 graded executions) attacks the system the way the doors actually face: injection through ingested content, figure forgery planted behind the store's back, approval spoofing, guardian bypass, and access probing under the Round 13 pack. An attack succeeds only if the protected invariant actually breaks — a forged figure on an approved/board/digest surface, a spoofed act accepted, a banned draft through the guardian. The full account — attack classes, grading, holes, fixes, limits — is `docs/red-team.md`.
- **Eight holes were open, and are closed.** Poisoned money (`"NaN"`, `"not-a-number"`, amounts too large to carry in cents) was accepted at the ingest port and crashed — or silently poisoned — every later computation; money fields now validate as finite, cent-carriable Decimals and the port refuses the rest. A banned phrase split across an email's subject and body, hyphenated (`guaran-teed`) or dotted passed the guardian; phrase matching is now separator-insensitive and reads the draft's texts in reading order, in the guardian and in the offline screening composer alike. A compound word percent was judged at its unit word ("thirty-five percent" read as five) and "half price" was invisible to the discount rule, while a bare "half" near any marker word blocked honest copy; compounds now parse whole, "half price" is judged as the fifty-percent promise it is, and word discounts require the pack's stated pairing. Disparagement split across two sentences passed; it is judged per text now. And a presented caller could record an approval or rejection naming a different person; the act must now name the human who acted, and a mismatch is refused and recorded.
- **What held from the start.** Forged drafts (claims edited after drafting, a payload claiming approved status), forged and rebound guardian verdicts, a tampered ledger (its verifier names the mismatch, the compute path returns the genuine artefact, and the plan and board refuse rather than state the figure), forged approval acts claiming "sent" or bound to missing verdicts, an instruction planted in a flow name, and unresolvable identities probing every surface — all refused, inert, or existence-hidden before this round touched anything.
- **Stated limits.** Pack-list synonyms and letter substitutions (leetspeak, homoglyphs) are not judged by the code rules — the model-judged rules on the hosted profile are the semantic net, and offline the screener judges the same stated lists. An absolute-amount promise ("$40 off") states no percent to judge against the cap (the figure rule still applies). Phrase pieces separated by a whole intervening text are not one phrase to the reader, and are not matched. Guardian pack version bumps to `2026.11.1` for the judgement changes, the prior pack retained for verify. The demo plants a second bad draft the sneaky way — hyphenated promise, "half price" — and shows the screen blocking it. No migration was needed.

## What Round 18 builds

- **Scoped tokens: the presented identity, authenticated.** Round 13's callers present a name and a role; a token proves the presentation. The owner issues a token to a named actor with a role and an explicit scope set — a subset of the access pack's permissions, and issuance is refused (named reason, nothing recorded) when a scope would exceed the role, so a token can only ever narrow. The secret is 32 bytes from a CSPRNG, shown exactly once in the issuance result; the record stores a per-token salt and a salted PBKDF2-HMAC-SHA256 over the secret's SHA-256 digest — the digest step matters, because fed raw to the KDF the secret is an HMAC key and HMAC zero-pads short keys, so a secret extended with zero bytes would verify as the same key (the round's tests caught exactly that; over the digest, any byte difference is a different input). Tokens carry a stated TTL (30 days by default, at most a year), and expiry and revocation are derived from records on every read — revocation is a new record, nothing is deleted. Authentication resolves a bearer string to the same caller shape Round 13 defined, now carrying its scopes: effective permission is the role's permission intersected with the scopes, enforced at the same service boundary, so the API (an `X-SMB-Token` header or an `Authorization: Bearer` value) and the CLI (`--token`) cannot diverge — and when a token is presented it decides the caller alone: a forged string beside valid identity headers resolves to anonymous, never to the headers. A token caller acting outside its scopes is refused and the refusal recorded, deduped per token and permission. Reads of the token record are owner-gated metadata projections — id, actor, role, scopes, issued/expiry, derived status — and a test scans the stored record for the issued secret and finds nothing. Presented-identity calls keep working unchanged for the internal surfaces, the demo and the evals: the two coexist, with the token as the authenticated form of the same caller.
- **Webhooks: signed notifications, never documents.** The owner configures subscriptions — an endpoint URL, a set of event kinds, a signing secret — and the record's own transitions fire them: a draft passing the guardian into the approval queue, an approval act recorded, a batch quarantined whole, a digest generated, a review pack published. The payload is a notification under Law 2: the event kind, a delivery id, the subscription id, the time, the acting actor and the artefact ids involved — never a figure, never draft content; the figures stay behind the authenticated, role-gated reads, and a test asserts the ledger's headline figures appear in no delivery body. Deliveries are HMAC-SHA256 signed with the subscription's secret (the signature travels in the `X-SMB-Signature` header), and every attempt is recorded as its own artefact with the outcome and response class; retries are bounded at three attempts and a failing endpoint never fails the operation that fired the event. Delivery goes through a stated port: the production shape is an HTTP POST, and tests, the demo and the evals use a local double receiver that verifies the signature and keeps what it accepted and rejected — no real external HTTP call is made anywhere in tests, demo or evals. A verify helper (`GET /webhook-deliveries/{id}/verify`, CLI `webhook-verify`) re-performs a recorded delivery's signature from the record so a receiver can check it. The subscription's secret is shown once at configuration and stored encrypted at rest under a deployment key, never readable back; management sits behind the pack — owner-only write, gated reads, the same existence hiding. The eval gate carries five new zero-tolerance counters — `token_scope_escalations`, `revoked_token_actions`, `token_plaintext_leaks`, `webhook_payload_figure_leaks`, `unsigned_deliveries_accepted` — 77 in all. No migration was needed: tokens, revocations, refusals, subscriptions and deliveries are artefacts in the existing store.

## The laws

1. Money and metrics are computed in code (Decimal); the model drafts prose and proposals, never numbers. Any figure in a draft must resolve to a computed artefact or the draft fails verification.
2. Nothing leaves the building without two gates: the guardian screen, then a named human approval act bound to the draft's content hash. No act, no "approved" state anywhere.
3. Facts carry provenance (source system + as-of) or they are refused at the port.
4. Every plan, finding and draft is an insert-only, content-addressed artefact; supersession is by link, never by edit.
5. Anomaly and audit findings come from versioned packs with stated thresholds — the same inputs re-perform to the same findings, and a verifier re-performs every figure in a plan before it can be approved.
6. The model tier is a stated choice: Standard (no training on the data) is the default; Contributor must be selected explicitly and is badged wherever it is used, because Meta may train on prompts and outputs sent to it.
